This release adds two operational safety nets that were previously missing entirely — encrypted, scheduled backups with restore, and a reversible way to retire a ZEV instead of only deleting it outright — plus a guided metering import wizard. It also closes four security gaps, including one that let a client bypass per-IP rate limits by spoofing its own address; if you run `docker-compose.yml` or a reverse proxy in front of the backend, read Upgrading before you deploy this version.

### Backups: encrypted, scheduled, restorable

Under **System Settings → Backups**, an admin can back up the whole instance — or a single community — to a local directory or S3-compatible storage. Set `BACKUP_ENCRYPTION_KEYS` and it's AES-256-GCM encrypted; leave it unset and the backup is still written, but loudly: a warning banner on the tab, a stderr warning from the CLI, and a flag recorded on the job itself. A backup captures accounts, settings, every ZEV, invoice PDF files and the audit trail in one transaction.

Restoring the whole instance is a command-line operation (`manage.py openzev_restore --mode instance`) that refuses a non-empty database without `--force`, and refuses outright if the archive's migration state doesn't match yours. Restoring one community is friendlier: from the same Backups tab, a preview computes what would change against live data — new and changed rows, accounts it can't relink by email, any sent or paid invoice in the way — before anything is written, and a safety backup of that community is taken first so a bad restore can be undone. A daily or weekly schedule, retention (off by default — nothing is deleted until you turn it on), and a **Check** button that re-verifies a stored file's checksum round out the operational side; System Health gets a **Backups** card that turns stale after two missed scheduled runs.

Two caveats: restoring a community doesn't detect a bulk invoice generation already running against it (only another export or restore is), and S3 storage has so far only been tested against a fake client — smoke-test your actual bucket first. The Helm chart doesn't yet expose the new settings; set them as raw environment variables if you deploy that way.

### Retiring a ZEV: disable, archive, purge

An owner can now disable their own ZEV — **ZEV Settings → Export / transfer** — or an admin can disable or re-enable any ZEV from **Overview → ZEVs**. Disabling is reversible and changes nothing underneath: participants immediately lose read and write access, their invoice and onboarding links quietly stop resolving (indistinguishable from any other broken link), and no new invoices can be generated. The owner keeps read-only access; only an admin can turn it back on.

Once disabled, an admin can permanently delete a ZEV — **Purge**, which requires typing the ZEV's exact name to confirm. This removes every participant, metering point, reading, tariff and invoice underneath it; the audit trail and any issued contracts survive with the ZEV reference cleared, since they're the record it happened. There's no automatic safety backup before a purge — export a transfer archive or run a backup first if you want one.

The transfer archive itself can now optionally carry the original *issued* invoice PDFs, not just the billing data to regenerate them from — worth having since a regenerated PDF renders with today's template, not the one a participant actually received. Archives from before this version still import.

### Guided metering imports

**Metering → Imports** gets a preview-first wizard: it validates the file, flags meters it doesn't recognise, and shows what will change before anything is written. A daily file mixing readings you already have with new ones can now be re-imported without turning on overwrite — existing readings are kept, only the gaps are filled. Imports that did overwrite readings, including older ones, are now protected from deletion: a bulk delete touching one is rejected in full, nothing partially applied.

### Fixes worth knowing about

- **Per-IP rate limits could be bypassed by sending a fake `X-Forwarded-For` header.** The backend now resolves the client IP through an explicit trusted-proxy hop count (`NUM_PROXIES`, default 0), and the shipped nginx configs overwrite forwarded headers instead of passing them through. If you run your own reverse proxy, check `NUM_PROXIES` matches how many hops it actually adds — otherwise this protection is a no-op for you.
- **A ZEV owner could hard-delete their own community**, cascading away every participant, metering point and reading in it. Deletion is now admin-only, matching what the UI already implied.
- **Production-like Compose (`docker-compose.yml`) ran with development defaults** — `DEBUG` on, PostgreSQL and Redis ports published to the host. It now refuses to start without an explicit `backend/.env` and no longer publishes those ports; see Upgrading.
- Audit log writes are now committed in the same transaction as the change they describe, and malformed request metadata (an invalid request ID or IP) is stored as `NULL` instead of being written as-is.

### Upgrading

Six migrations, all additive — no downtime expected:

- `backups.0001`–`0003` — add `BackupDestination`, `BackupJob`, `RestoreJob` and their retention/verification fields
- `metering.0004`–`0005` — add warning and overwrite-count fields to `ImportLog`
- `zev.0027` — adds `disabled_at`, `disabled_by` and `disabled_reason` to `Zev`

New backend settings for backups, all optional (`backend/.env.example` has the full block): `BACKUP_ENCRYPTION_KEYS`, `BACKUP_S3_ACCESS_KEY_ID`/`BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_WORK_DIR`, `BACKUP_SAFETY_RETENTION_DAYS` (default 30). Backups are unencrypted until you set a key.

**If you run `docker-compose.yml`** (the production-like local stack): it now requires `backend/.env` with a real `SECRET_KEY` and refuses to start otherwise, and no longer publishes the PostgreSQL/Redis ports or the backend port directly — the API now reaches you through the proxy at `http://localhost:8080/api/v1/` instead of `:8001`. Fill in `backend/.env` from `backend/.env.example` before upgrading this stack.
