This release adds two safety nets that were missing entirely — encrypted, scheduled backups with restore, and a reversible way to retire a ZEV rather than only deleting it outright — plus a guided metering import wizard, and five security fixes. Two things before you deploy: onboarding links older than 30 days expire the moment you upgrade, and if you run `docker-compose.yml` or your own reverse proxy, read Upgrading first.

### Backups: encrypted, scheduled, restorable

Under **System Settings → Backup**, an admin can back up the whole instance — or one community — to a local directory or S3-compatible storage. A backup captures accounts, settings, every ZEV, invoice PDFs and the audit trail in one transaction. Set `BACKUP_ENCRYPTION_KEYS` and it's AES-256-GCM encrypted; leave it unset and it still runs, but warns on the tab, from the CLI and on the job record.

Restoring the whole instance is a command-line operation (`manage.py openzev_restore --mode instance`): it refuses a non-empty database without `--force`, and refuses outright if the archive's migration state doesn't match yours.  Restoring one community happens on the same tab: a preview shows what would change against live data — accounts it can't relink by email, any sent or paid invoice in the way — and a safety backup is taken first so a bad restore can be undone. There is also a daily or weekly schedule, retention (off by default), a **Check** button that re-verifies a stored checksum, and a System Health card that goes stale after two missed runs.

Caveats: restoring a community doesn't notice a bulk invoice generation already running against it; S3 has only been tested against a fake client, so smoke-test your real bucket; and the Helm chart doesn't expose the new settings yet — set them as raw environment variables.

### Retiring a ZEV: disable, archive, purge

An owner can now disable their own ZEV — **Settings → Export / transfer** — and an admin can disable or re-enable any ZEV from **Overview → ZEVs**. Disabling changes nothing underneath, but participants lose read and write access, their invoice and onboarding links stop resolving, and no new invoices can be generated. The owner keeps read-only access; only an admin can re-enable.

Once disabled, a ZEV can be permanently deleted — **Purge**, which requires typing its exact name. That removes every participant, metering point, reading, tariff and invoice underneath it; the audit trail and issued contracts survive with the ZEV reference cleared, since they're the record it happened. Nothing is backed up first, so export an archive or run a backup yourself if you want one.

The transfer archive can now optionally carry the original *issued* invoice PDFs, not just the data to regenerate them from — a regenerated PDF uses today's template, not the one the participant received. Older archives still import.

### Guided metering imports

**Metering → Import history** gets a preview-first wizard: it validates the file, flags meters it doesn't recognise, and shows what will change before anything is written. A daily file mixing readings you already have with new ones can be re-imported without turning on overwrite — existing readings are kept, only the gaps filled. Imports that did overwrite readings are protected: a bulk delete touching one is rejected in full.

### Also new

- Participant geocoding is now opt-in, since footprint lookups send addresses to OpenStreetMap's public Nominatim service. The participant map stays hidden, cached footprints included, until an admin turns on `participant_geocoding_enabled` under **System Settings → Functions**.

### Fixes worth knowing about

- **Per-IP rate limits could be bypassed by sending a fake `X-Forwarded-For` header.** The client IP now comes from an explicit trusted-proxy hop count (`NUM_PROXIES`, default 0), and the shipped nginx configs overwrite forwarded headers. If you run your own proxy, check `NUM_PROXIES` matches the hops it actually adds — otherwise this fix is a no-op for you.
- **Onboarding links never expired.** They now last 30 days, a participant holds one live link at a time, and setting or changing a password revokes the account's links. Resending an expired one issues a new secret. Logging out now ends every session on every device.
- **Deleting a ZEV from the list either crashed or destroyed everything under it.** It raised a 500 on any ZEV with invoices; on one without, it cascaded away every participant, metering point and reading. Button and endpoint are both gone — retiring a ZEV goes through disable, then purge.
- **Production-like Compose (`docker-compose.yml`) ran with development defaults** — `DEBUG` on, PostgreSQL and Redis published to the host. Both fixed; the stack now needs a real `backend/.env`, so see Upgrading.
- Audit log writes now commit in the same transaction as the change they describe, and malformed request metadata is stored as `NULL`.

### Upgrading

Eight migrations. Six additive; the two onboarding-link ones rewrite data:

- `backups.0001`–`0003` — add `BackupDestination`, `BackupJob`, `RestoreJob` and their retention/verification fields
- `metering.0004`–`0005` — add warning and overwrite-count fields to `ImportLog`
- `zev.0027` — adds `disabled_at`, `disabled_by` and `disabled_reason` to `Zev`
- `zev.0028` — dates every existing onboarding link's 30-day expiry from its creation, so **any link issued more than 30 days ago expires immediately on upgrade**. Resend from the participant's page.
- `zev.0029` — where a participant holds several live links, revokes all but the newest, then enforces one each. On PostgreSQL it briefly takes an exclusive lock on the onboarding-token table; don't run it with an old release still writing.

**Removed:** `DELETE /api/v1/zev/zevs/{id}/` now returns `405` for every role, admins included. A script that deleted a ZEV must now disable it (`POST .../disable/`), then purge it.

New backup settings, all optional (`backend/.env.example` has the full block): `BACKUP_ENCRYPTION_KEYS`, `BACKUP_S3_ACCESS_KEY_ID`/`BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_WORK_DIR`, `BACKUP_SAFETY_RETENTION_DAYS` (default 30). Backups are unencrypted until you set a key.

**If you run `docker-compose.yml`** (the production-like local stack): it now requires `backend/.env` with a real `SECRET_KEY`, and no longer publishes the PostgreSQL, Redis or backend ports — the API reaches you through the proxy at `http://localhost:8080/api/v1/` instead of `:8001`. Fill in `backend/.env` from `backend/.env.example` first.
