This release makes the metering import wizard do most of the work for you: it reads a file's settings, takes several files at once, and finally handles the one-file-per-OBIS-code exports Swiss grid operators send. If you have ever imported a feed-in file with **Overwrite existing readings** ticked, read the first fix below.

### The import wizard reads your file

Under **Metering → Import history**, **New Import** now looks at the file before asking you anything. It fills in the delimiter, header row, one-value-per-line versus one-day-per-row (with the number of values and the interval), the meter ID, date, energy and direction columns, and the date format. A note above the settings says what it found and what it could not, and **Detect again** discards your edits and re-reads. The settings are grouped into **File format**, **Column mapping** and **Options**.

Detection is a suggestion: it reads at most 60 sample rows, never touches your data, and the preview is still the step that decides whether anything is written. If it fails, you get the old defaults. SDAT-CH files have no settings to detect and are unaffected.

### Several files in one go

Select as many files as you like; each gets its own card and its own preview, and one file with errors blocks the whole import. All files share one set of settings, and the first file is the one detected, so select files that share a layout. Each becomes its own entry in the import history. If some fail, the rest stay imported and the wizard keeps only the failed files selected, so a retry does not import anything twice.

### Grid-operator exports with one file per OBIS code

Many distribution operators deliver a bidirectional meter as two files, grid import as `1.29.0` and feed-in as `2.29.0`, with the same meter ID and positive values in both. The `direction` column now accepts OBIS codes (`1.29.0`, `1-1:1.29.0*255`) as well as `in` and `out`, in both row layouts. Detection maps the column for you, and the preview gains a **Direction** column showing where the readings will land. Only active energy is understood: other OBIS codes, reactive energy included, reject the row rather than being guessed at.

### Also new

- **Dashboard → Per Participant** has a **From ZEV (%)** column: the share of each participant's consumption covered by the community rather than the grid
- Wide dashboard and billing tables scroll inside their card, with a frozen name column on the dashboard; billing row actions wrap instead of running off screen
- The feasibility calculator puts its results below the form on narrow screens or with the sidebar open, instead of squeezing both side by side

### Fixes worth knowing about

- **A second OBIS file could overwrite the first.** Without a direction column, feed-in values were read as consumption, so the feed-in file collided with the consumption file: skipped as duplicates, or, with overwrite on, written over the consumption readings and reported as a successful import. If you imported per-OBIS files this way, compare a metering point's `in` readings against the grid operator's original file; re-import the consumption file with overwrite and the feed-in file with its direction column mapped.
- **An explicitly mapped direction column that cannot be read is now an error.** It used to be ignored, silently falling back to the meter type. A saved mapping pointing at the wrong column will now stop the import with a message; leaving the field empty keeps the old inference.

### Upgrading

No migrations. One changed default: `IMPORT_THROTTLE_RATE`, the per-user limit on previews, detections and imports, rises from `60/hour` to `600/hour`, because detection and multi-file runs make several requests per file. If you set it explicitly, your value still applies and may now be too low for a multi-file run.

There is one new endpoint, `POST /api/v1/metering/import/detect-csv/`. Nothing is removed.
