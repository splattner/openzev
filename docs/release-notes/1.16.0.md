This release ships two-factor authentication — an authenticator app or a passkey — and closes two long-standing account-security gaps: your own profile could be re-pointed at another email without re-authenticating, and there was no way to end a session once it existed. The admin accounts console is also rebuilt around the account rather than the participant record. Two changes affect direct API use only — see Upgrading.

### Two-factor authentication

Enrol an authenticator app or a passkey under **Account → Security**. A passkey signs you in on its own; an authenticator app asks for a 6-digit code as a second step after your password. Either one also protects the password, magic-link and onboarding sign-in routes — a passkey-only account is prompted for one of its ten one-time recovery codes there instead of a TOTP code it has no way to produce. Recovery codes are shown once at enrolment and can be regenerated.

Admins can require 2FA by role, with a grace period, under **System Settings → Security**. Once the grace period ends, the requirement is enforced by the API itself, not just the app's UI: a session-cookie request from an overdue account gets blocked on writes (`403 mfa_enrolment_required`) until they enrol. API keys are exempt on purpose — a key has no sign-in moment to enrol at, so this can't lock a script out.

Losing both factors, or a passkey and its recovery codes, leaves only an administrator's reset (**Reset two-factor** on the accounts console) — there is no self-service way back in.

### Account security and session control

Two gaps closed after a review of self-service and login. `PATCH` on your own profile now only accepts your name and default community — a request that tries to change your email, username, role or active flag is rejected outright, not silently applied. Changing your sign-in email is its own flow instead: current password, then a confirmation link sent to the *new* address; applying it signs you out everywhere and emails the old address, so you'd notice if it wasn't you.

Sessions can also now be ended. **Sign out other devices** (Account → Security → Sessions) and, for admins, **Sign out everywhere** on another account's row both revoke every refresh token that account holds — previously nothing did, not even a password change, which now revokes them too (as does an admin's 2FA reset and deactivation). You'll get a short email whenever your account's security actually changes — a factor added or removed, recovery codes regenerated, your password changed, or an admin resetting your 2FA or signing you out everywhere — so a stolen session doing this quietly no longer goes unnoticed.

### Accounts console: one row per account

**Platform → Accounts → Users** is rebuilt around the account rather than the participant record: an owner of three communities, or a participant linked to one, is now a single row with a chip per community, instead of repeating across rows or looking like a standalone account with none. Each row also shows its second factors, whether it's meeting the 2FA policy (**2FA required · due `<date>`** or **2FA overdue**), and its last sign-in — or **Never signed in**, tracked correctly for the first time (it previously always read "never," even for daily logins, because none of this project's own sign-in screens raised Django's usual login signal). **View activity** on a row opens the audit log already filtered to what that account has done.

Admins can also **create** a platform account with no community — a second admin, a service account — and **deactivate**/reactivate one, both from the console. A created account gets a generated password shown once and must set its own at first sign-in; you can no longer deactivate your own account. Linking an account to a participant moves to the Participants page, next to the community it's joining.

### Also new

- The account page is now three tabs — **Profile**, **Security**, **API keys** — instead of one long scroll.
- A public landing page is live at [splattner.github.io/openzev](https://splattner.github.io/openzev), replacing the bare Helm-repo stub page; `helm repo add` is unaffected.

### Under the hood

The TOTP secret and recovery codes are encrypted at rest under a key independent of `SECRET_KEY` (ADR 0021), so rotating the app's own secret key can't turn into a mass 2FA lockout; `manage.py rotate_mfa_key` re-encrypts everything under a new key in one transaction. Session revocation is a single integer per account rather than a session table (ADR 0022), so it adds no per-request query. Passkeys replacing the password for their own login is ADR 0020.

### Upgrading

Four migrations, all additive:

- `accounts.0016` — creates `TotpDevice` and `MfaRecoveryCode`
- `accounts.0017` — adds `OAuthProvider.require_mfa_claim`
- `accounts.0018` — adds the `WebAuthnCredential` model and the MFA-policy fields on `AppSettings`
- `accounts.0019` — adds `User.session_version`, defaulting to 0, so nobody is signed out on deploy

No downtime expected.

Two-factor authentication is off until you set `MFA_ENCRYPTION_KEYS` (see `backend/.env.example` for how to generate one); passkeys additionally need `WEBAUTHN_RP_ID`, `WEBAUTHN_RP_NAME` and `WEBAUTHN_ORIGIN` to match your domain. New Helm values: `mfaEncryptionKeys` (or an existing secret) and `webauthn.*`. Two new throttle settings (`AUTH_MFA_THROTTLE_RATE`, `AUTH_EMAIL_CHANGE_THROTTLE_RATE`) and `EMAIL_TIMEOUT` ship with working defaults.

**Two breaking changes, both API-only** — the web app already follows these:

- `PATCH /auth/me/` now rejects a payload that changes `email`, `username`, `role`, `must_change_password` or `is_active` with a `400` instead of applying it.
- Once an account is overdue on the MFA policy, session-cookie requests making a write get `403 mfa_enrolment_required`. A script should switch to an API key, which this check does not apply to.
