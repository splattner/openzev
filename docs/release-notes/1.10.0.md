This release adds a printable tariff overview. The rest is fixes — three worth
checking your own instance against: a scripted deletion could clear a meter's
whole reading history, participants could read metering data from outside their
assignment window, and an owner with a participant record could silently lose
management access.

### Tariff overview PDF

Tariffs were the one participant-facing thing a ZEV could not print. Invoices,
statements and contracts all had a document; the prices existed only as rows
behind a login.

**Tariffs → Tariff overview (PDF)** downloads every tariff in force today,
grouped by category in the invoice's own order. Owner and admin only.

![Tariff overview table with four category blocks: Energy, holding a flat grid
tariff at 29.50 Rp./kWh and a two-band community solar tariff at 22.50 and
18.00; Grid fees, with seasonal winter and summer bands; Levies, showing
18.00 % × 29.50 Rp./kWh resolving to 5.31; and Metering, with a shared monthly
fee of 8.00 CHF/mo. labelled "Community costs, split
equally"](screenshots/1.10.0-tariff-overview.png)

Every band gets its own row, named as the participation contract and the
band-itemised invoice already name it, and a percentage-of-energy tariff shows
the formula behind its rate. A shared fee prints what the *community* pays and
says how it splits, so the figure is not misread as one participant's share.
The document states the ZEV's VAT treatment: under VAT-inclusive mode a note
says the prices are net, because the invoice grosses them per line and the
number here is deliberately not the number a participant is billed.

Switch the page's validity filter to "All tariffs" first to include superseded
and future versions. There is no date picker — the overview always reflects
today, though the endpoint takes an `as_of` parameter. It is not a customisable
template, and there is no per-kWh total or price history. No migration: it is a
projection of stored tariff data.

### Fixes worth knowing about

- **A scripted reading deletion could wipe a meter's entire history.** The
  delete-readings endpoint parsed `delete_all` with Python's `bool()`, so the
  *string* `"false"` — what a form-encoded `curl -d delete_all=false` sends —
  read as true and dropped the date filter. The request is now validated before
  anything is deleted. The endpoint is admin-only and the **Metering Points →
  Delete data** dialog always sent a real boolean, so only scripts could hit it.
  If you have ever deleted readings from a script, check that meter against your
  import logs.
- **Participants could read metering data from outside their own assignment
  window.** Readings were scoped to the meters someone is assigned to but not to
  the dates they held them, so a new occupant saw the previous holder's
  consumption, and a departed one kept seeing the meter. **Metering Data** and
  the raw-data view now match each reading against an assignment covering its
  own UTC date. Owners and admins are unaffected.
- **An owner or admin with a participant record could be demoted.** Syncing a
  participant's profile set the linked account's role unconditionally, so
  editing that person's details — or inviting them — stripped their management
  access. Owner and admin roles are now preserved; linked guests still become
  participants. Restore a lost role under **Admin Console → Accounts &
  Participants**.
- **The metering chart bucketed in local time while filtering in UTC.** Day and
  month bars were cut on Zurich midnight inside a UTC-filtered range, so chart
  totals could disagree with the raw-data table for the same period, and the
  October DST fallback merged two hours into one bar. Buckets are UTC now.
  Billing was never affected — the allocation engine has always resolved
  timestamps in UTC (ADR 0007).
- **Editing a metering point could blank the page.** Toggling **Active** a
  second time read an `event.currentTarget` that React had already nulled, which
  unmounted the page. Same fix on the assignment form's dropdowns and the admin
  OAuth switch. No data affected.

### Under the hood

Batch generation — invoice batches, PDF batches, annual-statement ZIPs — rebuilt
the same ZEV-wide calculations for every participant, and now builds them once
per batch. On the 12-participant fixture that is 15–50% fewer queries (an
invoice-PDF batch: 256 → 131), though wall time is dominated by PDF rendering.
Per-document failure isolation (ADR 0011) is unchanged.

### Upgrading

No migrations, no configuration changes, no downtime. Three API behaviour
changes, all consequences of the fixes above:

- **`delete-readings` validates its request.** A script sending `delete_all` as
  the string `"false"` now gets the bounded deletion it asked for. Validation
  errors are keyed by field rather than a single `{"error": "…"}` string.
- **Participant reading queries return less.** `chart-data` and `raw-data`
  exclude readings outside the caller's assignment windows; reconcile a meter's
  full history as an owner or admin instead.
- **The annual-statement ZIP returns 500** on a failed shared calculation,
  instead of 200 with an empty archive.
