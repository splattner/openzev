This release adds a printable tariff overview — the prices a ZEV charges, as a
PDF you can hand out or file. The rest of it is fixes, and three of them are
worth checking your own instance against: a scripted deletion could remove a
meter's entire reading history, participants could read metering data from
outside their own assignment window, and an owner or admin who also has a
participant record could silently lose management access.

### Tariff overview PDF

Every other participant-facing document a ZEV produces — invoice, annual
statement, financial summary, participation contract — has a printable form.
The tariffs did not: they existed only as rows on the **Tariffs** page, behind
a login. That left four situations with no good answer — a participants'
meeting where prices are what people ask about, a price change to communicate
after an Art. 7b import, the archive ("what were our prices on this date"), and
a participant checking a bill.

**Tariffs → Tariff overview (PDF)** on the page toolbar now downloads a PDF
listing every tariff in force today, grouped by category (Energy, Grid fees,
Levies, Metering) in the same order an invoice groups its line items. Owner and
admin only.

- **One row per price band**, named with the same wording as the participation
  contract and the band-itemised invoice added in 1.9.0: HT/NT, a seasonal
  band's month range, a plain band's weekday-and-time window. One band, one
  name, across all three documents.
- **A percentage-of-energy tariff** prints its formula — e.g.
  `18.00 % × 29.50 Rp./kWh` resolving to `5.31 Rp./kWh` — derived from the same
  grid tariffs the participation contract uses, via a helper now shared by both
  documents. Where that grid tariff has more than one band, a footnote says the
  figure shown is the base rate, not the per-timestamp price the billing engine
  actually resolves.
- **Prices are shown in Rp./kWh**, the convention on the contract and on every
  Swiss tariff sheet — not the five-decimal CHF/kWh the invoice carries because
  it multiplies by consumption.
- **A shared fee** states how it is split (equally, or by weight) and prints
  what the whole community pays, not one participant's share — otherwise the
  number reads as a per-participant amount and is wrong by the size of the ZEV.
- **The document states the ZEV's VAT treatment.** Under VAT-inclusive mode the
  stored prices are net and the invoice grosses them per line, so a note says
  the prices here are net — the number on this document is deliberately not the
  number a participant is billed. For a VAT-registered ZEV the note says prices
  exclude VAT and prints the VAT number.
- **To include superseded and future versions**, switch the page's own
  validity filter from "Valid only" to "All tariffs" before downloading; those
  rows print greyed out with their full validity span instead of "from …".

What it deliberately does not do: there is no date picker — the overview always
reflects today (the endpoint accepts an `as_of` parameter, so a picker is a
later frontend-only addition if it is wanted). It is not a customisable
template, matching the financial summary. There is no per-kWh "what a grid
consumer pays" summary line yet, and no price-history chart. No model changes
and no migration — it is a straight projection of stored tariff data.

### Fixes worth knowing about

- **A scripted reading deletion could wipe a meter's entire history.** The
  delete-readings endpoint read its `delete_all` flag through Python's `bool()`,
  which treats *any* non-empty string as true. A form-encoded request — the
  shape `curl -d delete_all=false -d date_from=… -d date_to=…` produces — or a
  JSON body carrying the string `"false"` therefore skipped the date filter
  entirely and deleted every reading on the meter. The request is now validated
  before anything is counted or deleted: `"false"`, `"0"` and `"off"` all mean
  false, an unrecognised value is rejected with a 400, and a missing or reversed
  date range is refused without writing. The endpoint is admin-only and the
  **Metering Points → Delete data** dialog has always sent a real JSON boolean,
  so the UI never triggered this — only scripts and integrations could. If you
  have ever deleted readings from a script, compare that meter against your
  import logs.

- **Participants could read metering data from outside their own assignment
  window.** A participant's readings were scoped to the meters they are assigned
  to, but not to the dates they held them. Someone who moved into a flat could
  see the previous holder's consumption on that meter, and a departed holder's
  data stayed visible to them after they left. Both the **Metering Data** chart
  and the raw-data view now match each reading against an assignment that covers
  the reading's own UTC date, so a participant sees only their own occupancy —
  gaps between windows, and any intervening holder, are excluded. Admins and ZEV
  owners are unaffected and still see every reading on their meters.

- **An owner or admin with a participant record could be demoted to
  participant.** Syncing a participant's profile set the linked account's role
  unconditionally, so editing that person's participant details — or sending
  them an invitation — stripped their management access. This bites exactly the
  people most likely to have a participant record of their own: a ZEV owner who
  also consumes from the community. Owner and admin roles are now preserved; a
  linked guest account still becomes a participant. If an owner has lost access
  to their own community, this is why, and their role can be restored under
  **Admin Console → Accounts & Participants**.

- **The metering chart bucketed by local time while its filters used UTC.** Day
  and month bars were cut on Zurich midnight, but the date range around them was
  filtered on UTC midnight, so the chart's daily totals could disagree with the
  raw-data table for the same period and readings in the last hour or two of a
  UTC day landed on the neighbouring bar. During the October DST fallback the
  two distinct UTC hours collapsed into a single hourly bar. Buckets are now
  truncated in UTC, matching the raw data and the filters. Billing was never
  affected — the allocation engine has always resolved timestamps in UTC
  (ADR 0007).

- **Editing a metering point could blank the page.** Toggling the **Active**
  switch on the metering-point form a second time threw an error that unmounted
  the page: the handler read `event.currentTarget` inside a deferred state
  update, by which point React had nulled it. The first toggle worked, the
  second crashed. The same pattern was corrected on the assignment form's
  dropdowns and on the admin OAuth "enabled" switch. No data was affected and
  the page recovered on reload, but the edit could not be completed.

### Under the hood

Batch document generation — invoice batches, invoice-PDF batches and
annual-statement ZIPs — rebuilt the same ZEV-wide calculations (participant
weight windows, per-date and per-tariff weight sums, community totals) once for
every participant. Each batch now builds them once per ZEV-period and reuses
them; single-document generation is untouched. On the 12-participant fixture
the SQL statement count per batch drops by roughly 15–50% — an invoice-PDF
batch goes from 256 to 131 — though wall-clock time is dominated by PDF
rendering and moves only a few percent. Per-document failure isolation
(ADR 0011) is preserved: a failure in the shared setup is logged once and still
produces one failure entry per affected participant.

### Upgrading

No migrations, no configuration changes, no downtime.

Three behaviour changes for API clients, all of them consequences of the fixes
above:

- **`POST /metering-points/{id}/delete-readings/` validates its request.**
  `delete_all` is now parsed as a proper boolean, so a script that sent the
  string `"false"` and relied — knowingly or not — on the whole meter being
  cleared will now get the bounded deletion it asked for. Validation errors
  changed shape with it: a 400 is now keyed by field (`{"date_from": ["This
  field is required when delete_all is false."]}`) rather than the previous
  single `{"error": "…"}` string.
- **Participant reading queries return less.** `chart-data` and `raw-data`
  called as a participant now exclude readings outside that participant's own
  assignment windows. A client that reconciled a meter's full history through a
  participant account will see fewer rows; run it as an owner or admin instead.
- **The annual-statement ZIP endpoint returns HTTP 500** when the shared yearly
  calculation fails, instead of HTTP 200 with an empty archive. A client that
  checked only the status code was previously handed a valid-looking ZIP with no
  statements in it.
