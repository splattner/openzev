## 1. Purpose

Accounts can come into being in eight ways and can authenticate in six, and the rules that
connect them (who may be signed in by an emailed link, who must hold a second factor, which
credentials a promotion retires) are spread over `accounts/`, `zev/` and `invoices/`. This
page is the one place that lists them together, with the special cases. It describes the
code as it is; it does not propose changes. The baseline for the user model and roles
remains [`2026-03-community-and-access.md`](2026-03-community-and-access.md) and for MFA
[`2026-09-two-factor-authentication.md`](2026-09-two-factor-authentication.md).

Verified against the code on 2026-10-14. Paths are relative to `backend/`.

> **Pending change.** [PR #1003](https://github.com/splattner/openzev/pull/1003) (open) changes
> how participant-only accounts keep a password: participant edits and link generation would stop
> clearing it, and a completed link login would carry a 15-minute `password_recovery_until` claim
> allowing `POST /auth/me/reset-password/`. This page describes `main` as of 2026-10-14; sections
> 3 (row 5), 5.1, 5.2 and 5.9 need revisiting when it merges.

## 2. Vocabulary

| Term | Meaning |
|---|---|
| Platform role | `User.role`: `admin` or `user` (`accounts/models.py::UserRole`). What an account may do in a ZEV comes from its access grants and participant rows, not from the role. |
| Participant-only account | An account created by `ensure_participant_account`: unusable password, no `must_change_password`, signed in only by participant links. |
| Protected / independent-login account | `requires_independent_login(user)` (`zev/services.py`): `independent_login_required`, or admin, or `may_create_zev`, or any `ZevAccessGrant`, or ever issuer/representative of a ZEV. Participant links must never sign these in. |
| Pending invitation | Inactive account with an unconsumed `EmailVerificationToken(purpose=invitation)`. |

## 3. Ways an account is created

| # | Path | Entry point | Initial state | First credential |
|---|---|---|---|---|
| 1 | Bootstrap | `manage.py createsuperuser` (`OpenZevUserManager.create_superuser` forces `role=admin`). `--noinput` reads `DJANGO_SUPERUSER_PASSWORD`. | Active admin | Password given at creation |
| 2 | Admin creates a user | `POST /auth/users/` (`UserListCreateView`, `IsAdmin`, `UserCreateSerializer`) | Active, `must_change_password=True` | Password typed by the admin, or generated by `generate_temporary_password()` (12 characters) and returned once as `generated_password` |
| 3 | Self-registration | `POST /auth/register/` then `POST /auth/verify-email/` | Inactive, `may_create_zev=True`, `must_change_password=True`, unusable password, until the signup token (24 h) is consumed | The verify link signs the user in; they then call `POST /auth/me/set-initial-password/` |
| 4 | ZEV access invitation | `POST /zev/zevs/<zev_id>/access/` with an email that has no account (`zev/views_access.py::ZevAccessListView.post`) | Inactive, unusable password, one `EmailVerificationToken(purpose=invitation)` (7 days) | Same `verify-email` flow; consuming an invitation sets `independent_login_required=True` |
| 5 | Participant rows | Participant create or update (`ParticipantSerializer.create/update` → `ensure_participant_account`); also reached by `link_account_for` | Active, **unusable password**, `must_change_password=False`, name/email copied from the participant. **Only when no account holds the address**; otherwise the existing account is linked as it is (section 5.6) | None. Signed in by a magic link or onboarding link (section 4) |
| 6 | ZEV setup with an owner | `create_zev_with_owner_setup` (`zev/services.py`) | Active, `must_change_password=True`. **Only for a new person**; with `owner.account` an existing account is used as it is and nothing is created (#1009) | Generated temporary password (none for an existing account) |
| 7 | OAuth auto-provision | First login of an unknown identity in `oauth_callback` | Active, `role=user`, no password | The identity provider |
| 8 | Demo seed | `manage.py seed_demo` | Active | Fixed demo passwords (`admin@openzev.local` / `admin1234`) |

Not a creation path: the ZEV transfer archive carries no accounts and never re-links them
(`zev/transfer/importer.py`). Instance restore (`backups/restore.py`) replaces a bootstrap
superuser.

Other ways access is *attached* to an existing account:

- `POST /zev/participants/<id>/link-account/` (admin only; admin accounts cannot be linked)
  and `…/unlink-account/` (admin only; also revokes the participant's onboarding links;
  refused if it would leave a ZEV without a manager).
- A grant for an existing email (`ZevAccessListView.post`): sends `send_granted_notice`
  when the account already has a login, an invitation when it has none.

## 4. Ways to authenticate

| Method | Endpoint | Notes |
|---|---|---|
| Password | `POST /auth/token/` (`CustomTokenObtainPairView`, scope `auth_login`) | Accepts `email` (case-insensitive; an address belongs to at most one account) or `username`. Answers `{mfa_required, mfa_token, methods}` instead of a session when the account has a TOTP device or a passkey. |
| Second factor | `POST /auth/token/mfa/` (`TokenMfaView`) | TOTP or recovery code against a 5-minute signed challenge (`mfa.MFA_CHALLENGE_TTL`). |
| Passkey | `POST /auth/passkeys/authenticate/begin/` and `…/complete/` | Passwordless, `userVerification: required`; never asks for a further factor. Sign-count regression is refused and audited. |
| OAuth / OIDC | `POST /auth/oauth/login/<slug>/` → provider → `GET /auth/oauth/callback/<slug>/` → `POST /auth/oauth/token-exchange/` | Providers are configured by an admin (`/auth/oauth/providers/config/`). State lives 10 minutes, the exchange code 60 seconds. Linking an identity to a signed-in account: `POST /auth/oauth/link/<slug>/`; unlinking: `DELETE /auth/me/social-accounts/<id>/`. |
| Magic link | `POST /public/magic-link/request/` and `…/consume/` (`accounts/magic_links.py`) | Reached from an invoice link. The requester never types an address; the mail goes to the address on file. Single use, 15 minutes, a new request supersedes the old one. |
| Onboarding link | `POST /public/onboarding/consume/` (`zev/onboarding.py`) | Sent or copied by a manager. **Reusable, not consumed**, 30 days, revocable. Frontend route `/join/:prefix?s=…`. |
| Email verification | `POST /auth/verify-email/` | Signup (24 h) and invitation (7 days) tokens; consuming one activates the account and signs it in. |
| API key | `Authorization: Api-Key ozv_…` | Created at `POST /auth/me/api-keys/`. Default expiry `API_KEY_DEFAULT_EXPIRY_DAYS` (365). Optional `read_only`. |
| MCP | `Authorization: Api-Key ozv_…` or `Bearer ozv_…` on `/api/v1/mcp/` | Same keys, `McpApiKeyAuthentication`. Gated by the `mcp_server_enabled` feature flag. |
| Impersonation | `POST /auth/users/<id>/impersonate/` (admin) | Not a credential: an admin session acting as an active non-admin account. |

Sessions are JWTs in httpOnly cookies (access 60 minutes, refresh 7 days, rotated) or a
`Bearer` header. `CookieJWTAuthentication` enforces CSRF for cookie-borne unsafe requests.

Credentials an account can end up holding: password, passkeys (many), one TOTP device plus
recovery codes, linked OAuth identities, API keys. `has_login_credentials(user)`
(`zev/services.py`) counts a usable password, an enabled OAuth identity or a passkey.

## 5. Special cases

### 5.1 Independent-login protection

- `User.independent_login_required` is set when the account becomes admin, superuser, or
  `may_create_zev` (in `User.save`), and when an invitation is accepted. It is sticky: it
  survives demotion.
- Participant links (magic and onboarding) refuse protected accounts (`LinkRefused`, code
  `own_login_required`); the endpoints answer as for an unknown link and audit the refusal.
- `ensure_participant_account` leaves a protected account's password, email and name alone.
  For any other linked account it **clears an existing password** (changed by #1003), clears
  `must_change_password`, and copies the participant's email and name onto the account.
- Promoting an account (`protect_account_login`) first requires `has_login_credentials` or a
  pending invitation (`validate_account_login`: "Send an access invitation before assigning
  independent access"). It then bumps `session_version`, revokes active API keys, onboarding
  links and magic links, and sets the flag unless an invitation is still pending.
- A party holding the issuer or representative role with no account cannot be given a
  participant login (`link_account_for` → `login_setup_required`); it needs an invitation.
- Only an admin may invite or edit an account that is protected, outside the inviter's ZEV,
  or linked to participants in other ZEVs.

### 5.2 Participant-only accounts

- No password, so `POST /auth/me/email-change/` is refused (`code: no_password`).
- A participant may set a password after signing in through a link
  (`set-initial-password`); that revokes all sessions and the participant's onboarding links,
  and the account keeps the password afterwards.
- `consume` of a magic link also clears `must_change_password` and sets an unusable
  password if the account somehow had a temporary one.

### 5.3 Second factor by door

| Door | Challenged for a local factor? |
|---|---|
| Password login | Yes, if a TOTP device or passkey exists |
| Magic link, onboarding link, email verification | Yes, same rule (link already spent for magic links) |
| Passkey login | No — it is the factor |
| OAuth login | **No.** The IdP owns authentication. A provider with `require_mfa_claim` refuses the login unless `amr` names an MFA method (`mfa.OAUTH_MFA_AMR_VALUES`; `pwd` alone does not count) |
| API key / MCP | No; keys cannot reach the MFA surface |

`AppSettings.mfa_required` is a single instance-wide switch (needs `MFA_ENCRYPTION_KEYS`).
After `mfa_grace_period_days` it blocks unsafe methods for interactive sessions through
`enforce_mfa_enrolment`, except the enrolment ceremony, password change, sign-out and
similar (`MFA_ENROLMENT_EXEMPT_URL_NAMES`). Impersonated sessions and API keys are exempt.

### 5.4 API keys

- The `accounts` app is **default-deny** for keys (`ACCOUNTS_API_KEY_ALLOWLIST`): only
  `me`, `app-settings`, `feature-flags-list`, `registration-enabled`, `user-list-create`
  and `user-detail` (read-only), and `vat-rate-*`. A key cannot mint a session, manage
  MFA, passkeys, keys, email or sessions, or impersonate.
- Key management endpoints (`me/api-keys/…`, admin `api-keys/…`) are absent from the
  allowlist, so a leaked key cannot create a replacement or revoke others.
- Promotion revokes the account's keys; a participant key cannot inherit grants.
- An overdue-MFA account can still *delete* a key but cannot create or rename one.

### 5.5 Sessions

`session_version` is carried in every token as claim `sv`; a token whose value no longer
matches is refused. It is bumped (`revoke_sessions`) on: logout (which signs out everywhere), password change, initial
password set, email change, "sign out everywhere" (own or by an admin), deactivation by an
admin, admin MFA reset, and promotion. Reactivating an account does not revive older tokens.
`User.save` never writes the column, so a stale instance cannot undo a revocation.

### 5.6 Email

- `User.email` is **unique, case-insensitively, among non-blank addresses**
  ([#1005](https://github.com/splattner/openzev/issues/1005); `UniqueConstraint` on `Lower(email)`,
  `accounts.0027`). The address is the account's identifier, so sign-in, OAuth matching,
  invitations and participant links each find at most one account. Blank is allowed.
- Every creation path checks the address first: `POST /auth/users/`, `PATCH /auth/users/<id>/` and
  the wizard's `owner.email` answer 400, registration and invitations treat a taken address as an
  existing account, and the email-change confirmation refuses a taken address.
- Participant rows **reuse** the account that holds their address instead of creating another
  (`zev.services.account_for_email`, `ensure_participant_account`): rows with one address, in one
  ZEV or several, share one account. The existing account keeps its credentials, email and name,
  and a non-admin cannot attach a row to an account with its own login. A row whose address
  changes moves a sole account along, relinks to the account holding the new address, or, when
  other rows share its account, gets an account of its own.
- `accounts.0026` folded the duplicates that existed before the constraint: participant-only
  accounts were merged into the strongest account for the address (participant rows and parties
  moved, the empty account deleted); an account with a login of its own that could not be folded
  lost its address and keeps its username.
- Email change (`me/email-change/` → `confirm-email-change/`) needs the current password, a
  signed 24-hour link to the new address that dies when the password or address changes, and
  notifies the old address.
- `POST /auth/register/` always answers 201 with the same text, whether or not the address
  is usable; a 15-minute per-address mail cooldown is held in the cache and the request
  fails closed (`RegistrationUnavailable`) if the cache is down.

### 5.7 OAuth

- A new identity is matched to an existing account by email only when the provider asserts
  `email_verified: true`. A new account is provisioned only on the same condition, unless the
  provider has `trust_missing_email_verified` and omitted the claim.
- A match that is inactive (including a pending invitation) is refused (`account_inactive`).
- **Provisioning does not check `zev_self_registration_enabled`.** With any provider enabled,
  anyone whom the IdP verifies can get an account (role `user`, no ZEV access). There is no
  domain or allow-list setting on `OAuthProvider`.
- The callback only redirects to the configured frontend URL; the exchange code is single
  use.

### 5.8 Self-registration

- Gated by the `zev_self_registration_enabled` feature flag (default on); the login page
  reads `GET /auth/registration-enabled/`.
- Re-registering a pending address resends a link and retires earlier ones after delivery.
  An address that already has an active account, an invitation, or any consumed token gets
  the same neutral answer and no mail.

### 5.9 Recovery

- There is **no forgot-password flow** ([#1006](https://github.com/splattner/openzev/issues/1006);
  also raised as a follow-up in the review of [#1003](https://github.com/splattner/openzev/pull/1003),
  which adds link-based recovery for participant-only accounts only).
  A user who has lost their password and has no passkey or OAuth identity depends on an
  operator: `createsuperuser`, the Django admin at `/admin/` (mounted only when
  `ADMIN_ENABLED`), or recreating the account.
- Admins can reset a user's second factor (`DELETE /auth/users/<id>/mfa/`), which bumps the
  user's sessions. Recovery codes (ten, single use) are issued with the first factor.

### 5.10 Impersonation

Admin and inactive targets are refused. The admin's own tokens are parked in backup cookies
and restored by `POST /auth/users/stop-impersonation/`. Both ends are audited
(`impersonation.issue_token`, `impersonation.end`).

### 5.11 Deleting accounts

`DELETE /auth/users/<id>/` is refused for the last admin, for accounts linked to a participant,
and for an account that is the last manager of a ZEV (`NoManagerLeft`). Each refusal is
audited as `user.delete` with status `denied`.

## 6. Audit trail

Sign-in and account events are recorded in the `auth` category, including `auth.login`
(with `method`), `auth.login_failed`, `auth.mfa.challenge_failed`, `auth.mfa.enrolled`,
`auth.mfa.enrolment_required`, `email.verify`, `password.set_initial`, `user.create`,
`user.update`, `user.delete`, `oauth.login`, `oauth.provision`, `oauth.provision_refused`,
`oauth.link`, `oauth.link_refused`, `oauth.unlink`, `oauth.login_failed`,
`invoice_link.magic_link_requested`, `invoice_link.magic_link_consumed`,
`participant_onboarding.consumed`, `impersonation.issue_token`, `impersonation.end`,
`zev_access.grant` and `zev_access.invite`. Failed password logins keep the attempted
identifier in the event.
